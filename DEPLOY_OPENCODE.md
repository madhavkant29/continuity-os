# OpenCode deployment and acceptance runbook

**Objective:** Deploy the ContinuityOS fictional-data judge demo over HTTPS and prove every Track 3 flow end-to-end. OpenCode should execute the commands, fix failures in the repository, then report a verified link with test evidence. Do not report a successful deployment until the public URL has been opened and the acceptance gates below have passed.

## 1. Initial inspection and secure configuration

- Work from the extracted repository root. Read `README.md`, `docs/GRAPH_MODEL.md`, `docs/SECURITY.md`, and `docs/HACKATHON_COMPLIANCE.md`.
- Inspect all changes with `git status`; preserve accurate commits and disclosures. Do not add creation/edit dates or calendar fields to the application. Do not falsify repository metadata.
- Set up an Ubuntu host with Docker Engine, Docker Compose plugin, Python 3, a DNS hostname pointing to that host, and inbound 80/443 allowed for HTTPS validation. Restrict SSH to the administrator's IP.
- Do not allow public inbound access to port 8000 or 6379, or use real organizational data.
- Prefer a dedicated host or VM. Do not replace or interrupt unrelated services on a shared VPS. Back up any existing FalkorDB named volumes before performing migrations.

```bash
python3 scripts/configure.py
# Choose a unique strong operator password. Keep the generated .env secret.
chmod 600 .env
```

Edit `.env` **without committing it**:

```dotenv
APP_MODE=demo
ENABLE_JUDGE_DEMO=true
PUBLIC_DOMAIN=demo.example.org
COOKIE_SECURE=true
ENABLE_LLM_ROUTER=false
```

Use your real DNS name instead of `demo.example.org`. Never echo or paste credentials into chat, commits or CI logs. Keep `FRONTEND_SESSION_SECRET`, `INTERNAL_API_KEY` and `FALKOR_PASSWORD` generated by the configuration script.

## 2. Run tests before exposing the app

```bash
python3 -m pip install -r backend/requirements.txt
PYTHONPATH=backend python3 -m pytest -q backend/tests
cd frontend
npm ci                     # if package-lock.json is present
# Otherwise npm install, verify, then commit the generated lockfile
npm run test
npm run lint
npm run build
cd ..
```

Fix any failed typechecking, dependency resolution, syntax or security tests. Pin a lockfile before final deployment. Never skip failed checks just to publish a URL.

## 3. Start the actual FalkorDB stack

```bash
docker compose config --quiet
docker compose -f docker-compose.yml -f docker-compose.public.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.public.yml up -d --build
docker compose ps
docker compose logs --tail=120 backend frontend falkordb caddy
```

Check that all application services become healthy and the TLS proxy provisions a valid certificate. Confirm actual startup of FalkorDB and that its data survives a container restart. The base Compose file publishes the backend to host loopback for local smoke tests; the firewall must deny external access.

## 4. Run mandatory live functional checks

**The local smoke script resets synthetic operator records; run it only on a disposable demo installation.**

```bash
python3 scripts/smoke.py
CONTINUITY_PUBLIC_ORIGIN=https://demo.example.org python3 scripts/smoke_judge.py
```

The judge smoke script creates two independent demo sessions and checks: seeded documents/tickets/chats; ticket ingestion with `PENDING_REVIEW`; exact line locators; reviewer action; source-cited analyst answer; Project and Passage graph nodes; continuity simulation; session isolation; and reset. The operator script tests actual graph-backed simulation, repair approval, drill and audit persistence.

If tests fail, read the containers' logs, fix the root cause, rebuild and rerun all tests. Do not patch out assertions.

## 5. Validate the public judge experience

- Visit `https://demo.example.org` in an incognito browser. Confirm the HTTPS certificate is trusted.
- Login should show **Explore live demo**. Press it; a fictional company dashboard should load without any signup or password.
- Select **Company sources** and verify the document/ticket/conversation list, import UI, source review, exact citation display and copy action. Ask the analyst for the imported ticket and verify its quoted content.
- Open the graph; confirm real Source, Passage, Project, Decision, Workflow, Skill, Permission and Person nodes. Change the active workflow and ensure graph content updates.
- Make the refund approver unavailable; confirm a `BLOCKED` simulation, a policy-safe repair suggestion, approval, a passed sandbox drill, and a persistent audit entry.
- Test a second private browsing session to confirm it cannot read the first judge's records.
- Confirm unauthenticated API requests are rejected and the private API key is never visible in browser requests, scripts or page source.
- Test refresh, keyboard navigation, mobile layout, errors, session expiration and reset.

## 6. Production exposure safeguards

- Public data must remain synthetic. Do not connect real IAM, finance, HR, ticketing or messaging accounts.
- Add **edge-level abuse protection**: rate limits for the public demo sign-in, source imports, agent calls, simulations, and overall requests. The in-process counter is not sufficient for a public multi-instance deployment.
- Enforce a maximum number of active guest graph namespaces and a documented maintenance procedure to delete abandoned judge graphs. Monitor disk consumption, graph persistence and backup/restore.
- Retain private FalkorDB authentication, service-to-service token, secure HttpOnly sessions and strict origin checks.
- Set up error/uptime alerts, bounded application and Caddy logs, sensible resource limits, dependency scanning, and restricted host firewall rules.
- Do not claim that the sandbox renewal updates real permissions or that the simulation executes real payments.

## 7. Submission deliverables

- Public repository with README, setup instructions, graph schema/Cypher queries, technically accurate architecture and source-citation examples.
- Demo video showing **evidence import → exact citations → graph relationships → blocked workflow → approved fictional repair → verification**.
- Public HTTPS URL, or complete Docker instructions if hosting is unavailable. Check the event's current submission form.
- Clearly explain why removing FalkorDB destroys the knowledge and constraint context. Disclose AI assistance and preserve truthful development history.

## Final reporting format for OpenCode

Return a concise checklist with: deployed HTTPS link, commit SHA, repository changes, backend tests, frontend tests/build, Docker health, operator smoke, judge smoke, browser workflow, security checks, unresolved failures, and release decision (**GO** or **NO-GO**). Never invent a completed check; show command output or screenshots where practical. No application-facing date or time fields.
